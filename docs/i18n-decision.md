# 다국어 전략 판단 — 처음부터 다국어 vs 한국어 우선

> 결론: **"둘 다 아님." 아키텍처는 다국어 지원으로 지금, 콘텐츠는 한국어 먼저, 확장은 공용 앱에 영어 우선.**

---

## 1. 질문을 두 개로 분리하라 (핵심)

흔히 뭉뚱그리는 두 결정은 비용 구조가 완전히 다르다.

| 결정 | 지금 하는 비용 | 나중에 바꾸는 비용 | 판단 |
|---|---|---|---|
| **A. 아키텍처** (i18n 지원 구조?) | 거의 0 (폴더 규칙+텍스트 분리) | **재앙급** (140개 재작업+URL변경+SEO붕괴) | **지금 한다** |
| **B. 콘텐츠** (실제 텍스트를 몇 개 언어로?) | 언어 수만큼 배수 | 언어 추가 = 점진 가능 | **한국어 먼저** |

➡️ 비싼 실수는 "한국어로 시작"이 아니라 **"확장 불가능한 한국어 전용 구조로 못 박는 것".**

---

## 2. 냉정한 요인 비교

| 요인 | 한국어 우선 | 처음부터 다국어 |
|---|---|---|
| 시장 크기 | ~7,700만 (좁음) | 영어권 수억 (넓음) |
| SEO 경쟁 | 낮음(언어 장벽=방어막) | 극악(calculator.net·Omni 장악) |
| RPM(수익 단가) | 낮음 $1~3 | 높음 $5~15(방문자당 3~5배) |
| 콘텐츠 제작비 | 1배 | 언어 수 배수 |
| 번역 품질/SEO | 네이티브=완벽 | 기계번역=감점 |
| 초기 속도/집중 | 빠름·검증 쉬움 | 느림·분산 |
| 은퇴(retrofit) 비용 | — | 막대 |

## 3. 140개 앱의 로케일 3분할 (번역은 앱별로 판단)

| 유형 | 비중 | 예시 | 번역 판단 |
|---|---|---|---|
| 🌍 글로벌 공용 | ~55% | BMI·단위변환·복리·이미지도구 전부·텍스트/개발도구 전부·룰렛·별자리·날짜계산·온도 | **번역 가치 최고**(텍스트 적음+RPM 높음) |
| 🇰🇷 한국 전용 | ~30% | 만나이·연봉실수령·4대보험·취등록세·내신·손없는날·양음력·전기요금·축의금 | **번역 금지**(개념 부재) |
| 🔀 데이터 현지화 | ~15% | 신발/의류/반지 사이즈·요리계량·팁 | 언어만 부착(이미 다국가 데이터) |

핵심: 공용 55%는 **번역이 가장 싸고(버튼 몇 개) RPM이 가장 높은(이미지·계산·변환) 지점** → 영어 확장 1순위.

## 4. 최종 판단 (실행 규칙)

1. **아키텍처 = 처음부터 다국어 지원 구조.** (지금 0원, 나중 재앙)
2. **콘텐츠 = 한국어 먼저 출시.** (집중·속도·네이티브·저경쟁으로 초기 트래픽/검증)
3. **확장 = 계획된 Phase 2.** 검증 후 **공용 55% 앱에 영어 우선 추가**(ROI 최대 지점).
4. **한국 전용 30% = 영원히 한국어.** (번역 = 낭비)

## 5. i18n-Ready 아키텍처 구현 규칙 (지금 정해둘 것)

### URL 구조 (SEO 필수)
```
/ko/bmi-calculator/      ← 한국어 (기본)
/en/bmi-calculator/      ← 영어 (Phase 2, 공용 앱만)
```
- 언어별 **독립 URL**(서브디렉토리 방식 권장: 관리 쉽고 도메인 권위 공유).
- 절대 쿠키/JS로만 언어 전환 금지(검색엔진이 각 언어를 색인 못 함).

### hreflang 태그 (지금 뼈대만, Phase 2에 값 채움)
```html
<link rel="alternate" hreflang="ko" href="https://site.com/ko/bmi-calculator/">
<link rel="alternate" hreflang="en" href="https://site.com/en/bmi-calculator/">
<link rel="alternate" hreflang="x-default" href="https://site.com/en/bmi-calculator/">
```

### 텍스트 분리 (하드코딩 금지)
```
/locales/ko.json   { "bmi.title": "BMI 계산기", "bmi.desc": "..." }
/locales/en.json   { "bmi.title": "BMI Calculator", ... }
```
- HTML에 문자열 직접 X → 키로 참조. 앱 1개 만들 때부터 이 패턴 적용.

### 앱 메타데이터에 로케일 태그
```
{ "id": "bmi", "scope": "global" }      ← 영어 확장 대상
{ "id": "manage", "scope": "ko-only" }  ← 번역 제외
```
→ Phase 2에서 `scope: global`만 자동 필터해 번역 착수.

## 6. 타임라인

| 시기 | 아키텍처 | 콘텐츠 |
|---|---|---|
| Phase 1 (0~6개월) | i18n-ready 구조 확정, `/ko/` 경로 | 한국어 앱 30~100개, 애드센스, SEO 검증 |
| Phase 2 (6~12개월) | `/en/` 경로 활성화, hreflang 값 채움 | 공용 55% 앱 영어화(RPM 높은 이미지·계산·변환 우선) |
| Phase 3 (12개월+) | 추가 언어(일/중/스페인어) 검토 | 트래픽·RPM 데이터로 언어 우선순위 결정 |

## 한 줄 결론
**"한국어로 시작하되, 영어로 확장할 길을 처음부터 열어둬라."**
처음부터 5개 언어 = 집중력 분산 실수. 한국어 전용 구조 = 미래를 죽이는 실수. 정답은 그 사이의 i18n-ready 하이브리드.
